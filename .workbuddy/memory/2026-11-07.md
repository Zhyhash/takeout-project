# 2026-11-07

## 修正 `applySnapshot` 终态冲突的非对称处理

### 问题
原实现对两个互斥终态的处理方向不同：
- `canceled` → 收到 `succeeded`：抛 `BusinessException` → 事务回滚 → 不记事件回执 → Webhook 非 2xx → Stripe 重投 3 天 → `recordWebhookFailure` 反复标 REVIEW。
- `succeeded` → 收到 `canceled`：`apply=false` 且状态不等 → 整个应用分支跳过 → **静默忽略但照常插入事件回执** → HTTP 200，Stripe 认为已处理，本地无 REVIEW 无日志。

后者更危险：钱被取消、本地仍 PAID、商家已推单，且没有任何痕迹。

### 判断
- 两种方向同样"几乎不可能发生"（Stripe 的 PaymentIntent 终态不可逆，本地只写可信快照），所以不存在"哪个方向更严重"的理由。
- 更关键的是**手段选错了**：Webhook 抛异常的含义是"请重投"，只适用于重投可能成功的场景（未绑定、DB 抖动、订单 CAS 短暂失败）。终态冲突重投一万次结果都一样，抛异常只会刷日志、反复改写协调状态。

### 改法
- 新增 `isTerminalConflict(previous, incoming)`，两个方向对称判断。
- 新增 `flagTerminalConflict(...)`：不抛异常、不改写支付/订单状态、`updateReconciliation(REVIEW, null)`、记事件回执（表示"已收到并转人工"）、`log.error` 带 previous/incoming。
- `applySnapshot` 里先判冲突再判终态回退。

### 测试
- 用例改名 `conflictingTerminalWebhookKeepsTheFirstTerminalStateAndFlagsReview`：不再 `assertThrows`，断言回执为 1。
- 新增 `lateCancellationForAnAlreadyPaidOrderIsFlaggedInsteadOfSilentlyIgnored`：覆盖原先被静默吞掉的方向。
- `StripePayment*Test + OrderPaymentNotificationTransactionTest`：82 项通过。
