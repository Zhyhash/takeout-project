## 商家拒单退款：三轮验收测试

新增测试（均不改动生产代码）：

- `src/test/java/org/example/takeout/Payment/Service/StripeRefundFlowTest.java`
  - 结构：`@SpringJUnitConfig` + H2(MODE=MySQL) + 真实 MyBatis/事务，只有 `StripeRefundGateway` 打桩；
    `OrderCommandService` 用 `Runnable::run` 同步执行 afterCommit 退款任务，测试无需等待。
  - 第一轮：拒单 → 订单 `REFUNDED`、退款 `succeeded/COMPLETE`、库存只归还一次（7→10）、
    创建参数为 `pi + amountMinor + order_refund_<orderId>`；另用 `retrieveRefund(落库 refundId)` 断言可回查。
  - 第二轮：重复拒单幂等（`newlyCreated=false` 不再归还库存/不再调网关）；重复同步同一 succeeded 快照
    走 `status 相同 + 已绑定` 的短路，不会因订单已 REFUNDED 而抛异常；
    本地 `PENDING` 且已有 `refundId` 时由 `recoverRefund()` 走 `retrieveRefund()` 收敛，且 COMPLETE 后为空操作。
  - 第三轮：用 H2 `CHECK (stripe_status <> 'succeeded')` 注入「远端创建成功、本地 sync 失败」，
    断言回滚后 `refund_id/stripe_status` 仍为空、`reconciliation_state=PENDING`、库存已归还且不回滚；
    恢复任务再次 `createRefund` 时两次幂等键相同 → 只有一笔退款、本地仍只有一条退款记录。
- `src/test/java/org/example/takeout/Payment/Gateway/StripeRefundSandboxLiveTest.java`
  - `@Tag("stripe-live")` + `@EnabledIfEnvironmentVariable(STRIPE_SECRET_KEY=rk_test_*)` 才执行；
    真实 Stripe 测试模式：`pm_card_visa` 确认 PaymentIntent → 创建退款 → retrieve 核对 → 同幂等键重放不产生新退款。

运行：`./mvnw -o -B -Dtest=StripeRefundFlowTest test`（6 passed），沙箱版默认 skipped。

## 商家超时未接单自动取消 + 复用退款链路

生产改动（最小范围）：

- `OrderMapper`：
  - 修正 `updateOrderStatusToRefunding` —— 之前被误加 `pay_time <= NOW() - INTERVAL 10 MINUTE`，
    会让"刚支付就拒单"直接失败；商家拒单必须不受 10 分钟限制，已移除该条件。
  - 新增 `updateOrderStatusToRefundingOnTimeout`（`status=PAID AND pay_time <= NOW()-10min`）
    与扫描 `selectUnacceptedPaidOrderIds`（只发现候选）。
  - `updateOrderStatusToPreparing` 保留 `pay_time > NOW() - INTERVAL 10 MINUTE`（接单窗口）。
- `StripeRefundTransactionService`：`prepareRefund(orderId, merchantId, timeoutCancellation)`
  私有主干；新增 `prepareTimeoutRefund(orderId)`，只跳过商家归属校验、改用超时抢占 SQL。
- `StripeRefundService.prepareTimeoutRefund` 透传。
- `OrderCommandService`：抽出 `settlePreparedRefund()`（归还库存 + afterCommit 提交 Stripe 调用），
  `rejectOrderByMerchant` 与新增的 `cancelOrderByMerchantTimeout` 共用；接单 SQL 未命中且状态仍 PAID 时
  给出"已超过接单时限"提示。
- 新增 `Order/Config/OrderAcceptTimeoutTask`（`@ConditionalOnProperty(payment.stripe.enabled)`，
  fixedDelay 60s，逐单 try/catch，BusinessException 视为正常竞争只 warn）。
- 删除 `FulfillmentService` 里遗留的空 `cancelOrderByMerchantTimeout` 存根（系统任务不经过商家域）。

测试：

- `OrderCommandServiceTest` 增至 21 个（接单超时提示、超时取消归还库存+afterCommit、重复取消、Stripe 未启用、已接单）。
- 新增 `integration/OrderAcceptTimeoutIntegrationTest`（8 个，真实 MySQL + 随机库）：
  10 分钟内可接单 / 超时不可接单 / 拒单不受时限 / 超时取消退款一次 / 已接单不被取消 /
  重复扫描不重复退款 / 接单与取消并发恰好一方成功（5 轮）/ 退款结果未知停在 REFUNDING 后由恢复任务收敛。
- 完整套件：1169 tests，0 failures，35 errors 全部来自需要本地 Redis 的既有测试（环境无 Redis）。
