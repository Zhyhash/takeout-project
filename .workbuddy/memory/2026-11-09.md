## Stripe 退款状态同步补全（Payment 模块）

- `Payment/Service/StripeRefundTransactionService#syncRefundStatus`：补全实现。
  - 入参/快照空值与 `refundId` 空值校验；订单不存在、退款记录不存在、退款对象不匹配均显式失败。
  - 新增金额与币种一致性校验（与本地退款记录比对）。
  - 首次绑定（本地 `refundId == null`）时查 `order_stripe_payments` 核对 `paymentIntentId`，并对 payment 记录缺失做了空安全处理。
  - 冲突路径改用新的 `updateReconciliationState`，不再构造半空实体走 `updateById`。
  - 状态机：`null/pending -> succeeded` 落 COMPLETE + 订单 REFUNDING→REFUNDED + 归还库存；`-> pending` 落 PENDING；`-> failed/canceled` 落 REVIEW 并 error 日志（订单保持 REFUNDING，交人工）。
- `Payment/Mapper/OrderStripeRefundMapper`：
  - `updateStatus` 调用处原为 2 参，签名需 4 参（补 `refundId`、`reconciliationState`）；SQL 增加 `AND (stripe_status IS NULL OR stripe_status='pending')` 作为终态不被覆盖的库级兜底。
  - 新增 `updateReconciliationState(orderId, state)`。
- 订单状态更新原调用不存在的 `orderMapper.updateStatus(orderId,"REFUNDING","REFUNDED")`，改为 `updateOrderStatusToRefunded(orderId, REFUNDING, REFUNDED)`（Integer 枚举码）。
- `./mvnw -o -DskipTests compile` BUILD SUCCESS。

遗留：`syncRefundStatus` 目前没有任何调用方（无退款 Webhook / 退款恢复任务）；`order_stripe_refunds` 无 `next_retry_at`/`retry_count`，pending 退款无法被自动恢复扫描；退款失败时订单会停在 REFUNDING。

### 后续修正：pending→pending 时漏绑定 refundId

- `syncStatus` 原幂等短路条件只有"状态相同"，导致首次同步远端就是 `pending`、本地 `stripeStatus` 也是 `pending` 时直接返回 UNCHANGED，`refund_id` 永远绑不上。
- 改为"状态一致 **且** 已绑定"才返回 UNCHANGED（`needsBind = refund.getRefundId() == null`）；未绑定继续走写入路径，`updateStatus` 的 SQL 本身带 `refund_id = #{refundId}`，顺带完成绑定；pending 分支返回 UPDATED（不触发库存回补）。
- 本地终态但缺 refundId 的异常数据仍走 CONFLICT → REVIEW。
