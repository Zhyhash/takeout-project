# 当前实际业务状态流转与最小闭环

## 一、文档目标

本文以当前 `OrderService`、`FulfillmentService`、`MerchantAccountService`、`DeliveryTaskService`、状态枚举和 Mapper 实现为准，记录用户、商家和骑手三方已经落地的最小业务闭环。

2026-10-28 核对：包含 `cancel_source` 取消来源、订单明细库存基准版本、骑手位置接口与配送任务 GEO。本文按当前工作区源码和 SQL 静态核对；本轮未运行测试、数据库迁移，也未连接真实 MySQL 或 Redis。

需要解决的问题包括：

- 三类主体分别可以执行什么动作；
- 每个动作允许从什么状态开始；
- 动作成功后改变什么业务事实；
- 哪些操作必须检查主体归属；
- 哪些操作存在重复请求或并发竞争；
- 骑手和配送任务是否应成为独立实体；
- 订单状态与配送任务状态如何保持一致；
- 哪些真实业务暂时不纳入 MVP。

------

# 二、核心设计结论

加入骑手后，系统不再只是简单的订单状态管理，而是形成三个相互关联、职责不同的业务实体：

```text
Order：用户购买与订单履约事实
Rider：骑手身份与账号信息
DeliveryTask：具体配送责任与配送过程
```

最终关系为：

```text
User ──创建──> Order <──归属── Merchant
                  │
                  │ 1 : 1
                  ▼
             DeliveryTask
                  │
                  ▼
                Rider
```

当前 MVP 中，一张订单最多对应一张配送任务。

生产环境 JWT 签名密钥必须由 `JWT_SECRET` 外部注入，仓库不提供默认值；密钥缺失或少于 32 字节时应用拒绝启动。

配送任务单向关联订单：

```text
DeliveryTask.orderId → Order.id
```

Order 暂时不必保存 `deliveryTaskId`，避免订单实体反向依赖配送实现。

------

# 三、为什么拆分 DeliveryTask

最小实现确实可以直接在订单表中增加：

```text
riderId
deliveryAcceptTime
deliveryTime
```

但当前配送行为已经具备独立的：

- 责任主体；
- 生命周期；
- 状态变化；
- 并发竞争；
- 时间记录；
- 未来配送费和骑手结算；
- 配送异常和重新派单可能。

因此，配送已经不再只是订单的几个附属字段，而是一个独立业务事实。

拆分依据不是单纯的“字段太多”或“方便扩展”，而是：

> 配送任务拥有独立生命周期和独立责任归属，不应全部塞入订单实体。

------

# 四、订单主状态机

订单负责表达用户购买和整体履约进度。

```text
WAIT_PAY
    │ 用户支付
    ▼
PAYING
    │ Stripe 可信 succeeded
    ▼
PAID
    │ 商家接单
    ▼
PREPARING
    │ 商家制作完成
    ▼
READY
    │ 骑手接取任务并开始配送
    ▼
DELIVERING
    │ 骑手确认送达
    ▼
DELIVERED
    │ 用户确认收货
    ▼
FINISHED
```

已有取消分支：

```text
WAIT_PAY → CANCELLED（用户主动取消 cancel_source=1，或超时取消 cancel_source=3；按库存基准版本尝试回补）
PAYING   → CANCELLED（Stripe 确认 canceled 且未收款，再按库存基准版本回补）
PAID     → CANCELLED（仅本地模拟订单商家拒单，cancel_source=2，按库存基准版本尝试回补）
```

`PAYING` 是已提交的支付资格，支付记录和稳定幂等键与资格同事务保存。Stripe 创建、查询和取消 HTTP 均在事务外，可信成功直接 `PAYING → PAID`，失败或未知结果不会回退到 `WAIT_PAY`。旧本地模拟支付只在 Stripe 关闭时使用，直接 `WAIT_PAY → PAID`。

真实退款尚未实现，有 Stripe 记录或启用 Stripe 时的已付订单不能通过商家拒单取消。只有既有无 Stripe 记录的本地模拟订单保留拒单退库；重复取消不重复回补。详见 [Stripe 支付重构报告](stripe-payment-refactor-report.md)。

# 五、订单状态业务定义

## 1. WAIT_PAY

### 业务事实

用户已经提交订单，订单已经创建，等待用户完成支付。当前代码在创建订单时已经扣减库存。

### 当前代码约束

```text
payTime == null
仅 WAIT_PAY 可以取消或发起支付
创建订单按整车结算：availableItems.size 必须等于 allItems.size
任一购物车项不可用时整个下单请求失败
```

------

## 2. PAYING

### 业务事实

`beginOrderPayment` 通过订单服务 CAS `WAIT_PAY → PAYING`，与支付记录、原始幂等键共同提交，再由编排服务在事务外请求 Stripe。

### 当前代码约束

```text
payTime == null
可信 succeeded 后在结果事务进入 PAID
请求失败或未知结果保留 PAYING，由数据库恢复任务处理
超过 30 分钟不能仅凭本地时间取消，需 Stripe 确认 canceled 且未收款
```

------

## 3. PAID

### 业务事实

用户已经完成支付，订单正式生效，等待所属商家接单。

### 当前代码约束

```text
payTime != null
商家只允许从 PAID 接单
```

------

## 4. PREPARING

### 业务事实

商家已经接单并开始制作餐品。当前 `Order` 实体没有保存商家接单时间。

### 当前代码约束

```text
order.status == PREPARING
尚未创建 DeliveryTask
```

------

## 5. READY

### 业务事实

商家已经完成制作，订单可以被骑手接取；同一事务内会创建配送任务。当前 `Order` 实体没有保存制作完成时间。

### 当前代码约束

```text
存在 status == WAIT_ASSIGN 的 DeliveryTask
DeliveryTask.riderId == null
```

`READY` 可以持续存在，并不保证立即有骑手接单。

------

## 6. DELIVERING

### 业务事实

骑手已经抢到配送任务并开始配送。当前 MVP 将“骑手接单”“到店取餐”和“开始配送”合并为同一个动作。

### 当前代码约束

```text
DeliveryTask.riderId != null
DeliveryTask.status == DELIVERING
DeliveryTask.acceptedTime != null
```

------

## 7. DELIVERED

### 业务事实

骑手已经确认送达，但用户尚未确认收货，因此订单还没有最终完成。

### 当前代码约束

```text
DeliveryTask.status == COMPLETED
DeliveryTask.deliveredTime != null
finishTime == null
```

------

## 8. FINISHED

### 业务事实

用户已经确认收到餐品，订单整体履约完成。

### 当前代码约束

```text
finishTime != null
DeliveryTask.status == COMPLETED
```

------

## 9. CANCELLED

### 业务事实

用户和原超时任务只取消 `WAIT_PAY`；Stripe 恢复任务取得可信 canceled 且未收款后可取消 `PAYING`。真实已付 Stripe 订单因退款尚未实现，商家拒单被阻止。未启用 Stripe 且无支付记录的本地模拟订单仍可拒单。取消与按明细库存基准版本回补共同提交，版本已变化的商品跳过回补。

### 当前代码约束

```text
用户取消：仅 WAIT_PAY → CANCELLED，写 cancel_source=1
超时取消：仅 WAIT_PAY → CANCELLED，写 cancel_source=3
商家拒单：仅无 Stripe 记录的本地模拟订单 PAID → CANCELLED，写 cancel_source=2
Stripe 取消：可信 canceled 且未收款时 PAYING → CANCELLED，写 cancel_source=3/4
用户重复取消：订单已为 CANCELLED 时直接返回，不重复归还库存
商家重复拒单：已是 CANCELLED 且 cancel_source=2 时直接返回，不重复退款、不重复归还库存
订单明细不能为空；为空时抛异常并回滚 CANCELLED 状态更新
历史已取消订单的 cancel_source 保持 NULL；平台来源=4 用于未超时但 Stripe 已取消的支付
```

库存回补以 `order_item.stock_version` 为依据。创建订单时，服务在事务内锁定商品行并读取当前 `product.stock_version`，按读到的版本完成预扣，再把该版本写入订单明细。商家只要显式提交 `stock`，即使新值与旧值相同，也会推进库存基准版本；预扣与回补本身不会推进该基准。这样在取消时，只会把仍属于当前库存基准的订单明细数量加回。旧基准明细被跳过不代表取消失败，订单状态和其余商品的回补仍在一个事务中完成。该保护避免旧订单回补覆盖商家后续重设的库存基准。

# 六、配送任务状态机

DeliveryTask 负责表达配送责任和配送过程。

当前 MVP 状态为：

```text
WAIT_ASSIGN
      │ 骑手接取任务
      ▼
DELIVERING
      │ 骑手确认送达
      ▼
COMPLETED
```

## WAIT_ASSIGN

配送任务已经创建，但尚未绑定骑手。

```text
riderId == null
acceptedTime == null
```

## DELIVERING

任务已经绑定骑手，骑手正在执行配送。

```text
riderId != null
acceptedTime != null
deliveredTime == null
```

## COMPLETED

骑手已经将餐品送达并结束自己的配送责任。

```text
riderId != null
deliveredTime != null
```

配送任务完成并不直接等于订单完成。

```text
DeliveryTask.COMPLETED
    ≠
Order.FINISHED
```

骑手完成配送后，订单进入 `DELIVERED` 并等待用户确认收货；用户确认后，订单才进入 `FINISHED`。

## 骑手位置（独立于订单与配送任务状态）

`RiderLocationService` 另用 Redis GEO `rider:locations` 保存坐标，以 ZSET `rider:last_active` 记录最后上报时间。`PUT /rider/location` 上报、`GET /rider/location` 读取、`DELETE /rider/location` 删除当前骑手自己的位置；JWT 角色检查后还会确认骑手账号仍处于有效状态。尚未上报时 GET 返回 `data = null`。服务不提供附近骑手查询。连续 5 分钟没有更新的位置符合清理条件，调度采用执行完成后等待 5 分钟（fixedDelay），每轮最多清理 10 批、每批 100 个位置。

这组坐标没有写入 `rider` 或 `delivery_task`，也不会推动 `WAIT_ASSIGN → DELIVERING → COMPLETED`。接单大厅读取当前骑手自己的位置作为附近任务查询圆心；位置服务本身不执行附近骑手搜索。详见[数据库结构文档](数据库结构.md)中的 Redis 骑手位置说明。

## 可接配送任务 GEO 索引

商家坐标在出餐时快照到 `delivery_task.pickup_longitude` 和 `pickup_latitude`。出餐事务提交后，`FulfillmentService` 按任务快照修复 `delivery:available:geo`；商家未配置坐标时跳过索引写入并记录日志。抢单数据库事务提交后删除对应 GEO 成员；删除失败时再按数据库当前状态尝试单任务修复。GEO 是发现和排序索引，任务能否被接取仍由 MySQL 状态和骑手归属决定。

定时全量对账启动后延迟 10 分钟，之后每轮结束等待 10 分钟。它用 MySQL 一条全量查询取得 `WAIT_ASSIGN` 且未分配骑手的任务 ID，用 Redis ZSET `range(0, -1)` 取得所有 GEO 成员，比较两侧集合差集并逐个修复差异成员。每个差异任务通过 `REQUIRES_NEW`、`REPEATABLE_READ` 和 `SELECT ... FOR UPDATE` 锁行，持锁完成 Redis 添加或删除；Redis 异常会回滚该单次数据库事务并留给下一轮重试。两侧均存在的成员不逐单重查坐标，因此差集对账不会校正已有成员的坐标漂移。

# 七、配送任务创建时机

当前 MVP 选择：

> 商家制作完成时创建 DeliveryTask。

即商家执行制作完成操作时，在同一个事务中完成：

```text
1. Order：PREPARING → READY
2. 创建 DeliveryTask
3. DeliveryTask.status = WAIT_ASSIGN
```

任务同时固化 `merchantName`、固定配送奖励 `5`、收货人姓名/电话/地址以及商家电话/地址。后续商家或用户资料变化不会改写已经生成的配送任务快照。

不在支付后立即创建配送任务，原因是当前项目不需要提前预测运力或提前调度。

大型平台可能在支付后提前生成配送需求，用于预测、派单和运力调度；但那属于调度效率优化，不是当前 MVP 闭环成立的必要条件。

# 八、动作业务契约

| 动作         | 执行主体       | 允许旧状态                                     | 主体归属检查                       | 成功结果                                                           | 当前重复请求语义                         |
| ------------ | -------------- | ---------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------ | ---------------------------------------- |
| 用户支付     | 下单用户本人   | 订单为 `WAIT_PAY`                              | `order.userId == 当前用户`         | 先进入 `PAYING`，成功后写 `payTime` 并进入 `PAID`                  | 已是 `PAID` 时返回业务异常               |
| 用户取消     | 下单用户本人   | 订单为 `WAIT_PAY`                              | `order.userId == 当前用户`         | 订单进入 `CANCELLED`，写 `cancel_source=1`，按库存基准版本尝试回补       | 已是 `CANCELLED` 时直接返回，不再次回补库存 |
| 商家接单     | 订单所属商家   | 订单为 `PAID`                                  | `order.merchantId == 当前商家`     | 订单进入 `PREPARING`                                               | 已是 `PREPARING` 时直接返回              |
| 商家拒单     | 订单所属商家   | 订单为 `PAID`                                  | `order.merchantId == 当前商家`     | 订单进入 `CANCELLED`，写 `cancel_source=2`，仅本地模拟订单按版本尝试回补库存     | 已由当前商家拒单且 `cancel_source=2` 时直接返回 |
| 商家制作完成 | 订单所属商家   | 订单为 `PREPARING`                             | `order.merchantId == 当前商家`     | 订单进入 `READY`，创建 `WAIT_ASSIGN` 配送任务                      | 已是 `READY` 且任务为未领取的 `WAIT_ASSIGN` 时返回；异常组合拒绝 |
| 骑手接取任务 | 当前骑手       | 任务为 `WAIT_ASSIGN`，订单为 `READY`           | 任务尚未绑定其他骑手               | 绑定 `riderId`、写 `acceptedTime`，任务和订单进入 `DELIVERING`     | 已由当前骑手接取且任务和订单仍为 `DELIVERING` 时返回 |
| 骑手确认送达 | 当前任务骑手   | 任务和订单都为 `DELIVERING`                    | `task.riderId == 当前骑手`         | 写 `deliveredTime`，任务进入 `COMPLETED`，订单进入 `DELIVERED`     | 当前骑手任务为 `COMPLETED` 且订单为 `DELIVERED` 或 `FINISHED` 时返回 |
| 用户确认收货 | 下单用户本人   | 订单为 `DELIVERED`                             | `order.userId == 当前用户`         | 写 `finishTime`，订单进入 `FINISHED`                               | 已是 `FINISHED` 时返回业务异常           |

# 九、强一致性与事务边界

当前项目是单体 Spring Boot 应用，Order 与 DeliveryTask 使用同一个数据库，因此不需要引入消息队列或最终一致性机制。

两个实体需要在关键动作中进行强一致更新。

实际事务入口为 `FulfillmentService.completePreparation`、`DeliveryTaskService.claimTask`、`DeliveryTaskService.completeDelivery`；这三个方法局部采用 `READ_COMMITTED`。预读商家/骑手后，等待另一个事务完成的重复请求回读时能看到已提交的最新状态，避免旧 RR 快照错误拒绝本应接受的重试。并发裁决仍依赖旧状态、归属及未领取条件更新，失败仍整体回滚；没有更改全库隔离级别。

## 1. 商家制作完成

同一事务内：

```text
Order：
PREPARING → READY

DeliveryTask：
不存在 → WAIT_ASSIGN
```

不能出现：

```text
Order 已经 READY
但 DeliveryTask 创建失败
```

否则订单已经可以配送，却不存在可供骑手接取的任务。

------

## 2. 骑手接取任务

同一事务内：

```text
DeliveryTask：
WAIT_ASSIGN → DELIVERING
绑定 riderId
写 acceptedTime

Order：
READY → DELIVERING
```

不能出现：

```text
配送任务已绑定骑手，但订单仍是 READY
```

也不能出现：

```text
订单已经 DELIVERING，但配送任务没有骑手
```

------

## 3. 骑手确认送达

同一事务内更新 DeliveryTask 和 Order：

```text
DeliveryTask：
DELIVERING → COMPLETED
写 deliveredTime

Order：
DELIVERING → DELIVERED
```

不能出现任务已经完成但订单仍在配送，或订单已经送达但任务尚未完成。任一步骤失败都会触发事务回滚。

------

## 4. 用户确认收货

检查：

```text
Order.userId == 当前用户
Order.status == DELIVERED
```

当前 `checkedOrder` 依赖骑手确认送达事务已经把订单推进到 `DELIVERED`，不会再次直接查询 DeliveryTask。

成功后：

```text
Order：
DELIVERED → FINISHED
写 finishTime
```

------

## 5. 商家拒单

同一事务内：

```text
Order：
PAID → CANCELLED
写 cancelSource = 2
仅无 Stripe 记录且 Stripe 关闭的本地模拟订单允许此路径
有 Stripe 支付记录时拒绝取消：真实退款尚未实现
按订单明细归还商品库存
```

不能出现订单已取消但库存未归还，或真实退款未实现却把已付 Stripe 订单标成 `CANCELLED`；任一后续步骤抛异常都会整体回滚。重复拒单通过条件更新失败后的状态和 `cancelSource` 判断，直接返回且不重复退款、不重复退库存。

# 十、并发与幂等设计

除创建订单外，当前动作大多属于已有实体上的状态迁移，因此可以依靠：

```text
旧状态条件
+
主体归属
+
条件更新
```

当前代码用受影响行数判断状态迁移是否成功，从而实现并发保护。幂等策略并不完全统一：用户取消、商家接单、商家拒单、制作完成和骑手操作支持目标状态幂等；支付和用户确认收货的重复请求会返回业务异常。只有创建订单使用 `requestId`。

## 普通状态迁移

例如商家接单：

```sql
UPDATE orders
SET status = PREPARING
WHERE id = ?
  AND merchant_id = ?
  AND status = PAID;
```

只有一条请求能够完成状态迁移。

------

## 骑手抢单

骑手接取任务是最高风险并发点。

配送任务更新条件为：

```text
task.status == WAIT_ASSIGN
task.riderId == null
```

任务更新成功后，再通过条件更新执行 `order.status == READY → DELIVERING`。两个更新位于同一事务中，订单更新失败时会回滚任务更新。

成功时必须同时：

```text
绑定 riderId
修改 DeliveryTask 状态
修改 Order 状态
写接单时间
```

并发结果：

- 一名骑手成功；
- 当前成功骑手重试时返回当前任务；
- 其他骑手返回“任务已被其他骑手接取”。

# 十一、主体权限检查

角色鉴权不能代替资源归属检查。

`JwtInterceptor` 对受保护请求读取 `HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE`，由 `AuthPathMatcher` 按已匹配的 MVC 模板判断角色；缺少模板时拒绝。编码路径映射到同一接口仍适用同一角色规则。公开白名单继续使用原 URI 判断，上传服务本身没有新增第二次商家身份校验。

## 商家操作

必须同时满足：

```text
当前账号具备商家身份
订单 merchantId 属于当前商家
订单状态允许该动作
```

当前不检查商家是否处于营业状态。

原因是营业状态主要决定是否接受新订单，不应阻止商家继续履行已经支付的存量订单。

------

## 骑手操作

必须满足：

```text
当前账号具备骑手身份
Rider 记录存在且 status == NORMAL
接单时任务尚未绑定其他骑手
后续操作时 task.riderId 属于当前骑手
```

当前身份来自 JWT 中的 `rider` 角色。`DeliveryTaskService` 在可接列表、当前任务、详情、抢单和完成操作前调用 `RiderService.requireActiveRiderId()` 查询 Rider 表；账号不存在或被禁用时直接拒绝。

------

## 用户操作

必须满足：

```text
当前账号具备用户身份
User 记录存在且 status == NORMAL
order.userId 属于当前用户
订单状态允许该动作
```

用户账号策略已变更：不再允许禁用用户登录。`UserService.login()` 仅为 `NORMAL` 用户签发 Token；每个用户角色的受保护请求在 `JwtInterceptor` 中调用 `UserService.requireActiveUserId()` 实时查询用户表。因此账号被禁用、未激活、注销或删除后，新登录和已有 Token 都会被拒绝。

------

# 十二、当前骑手端接口范围

## 已实现的骑手账号接口

```text
POST /rider/register
    注册骑手，默认状态 NORMAL

POST /rider/login
    校验密码与账号状态，签发 rider 角色 JWT
```

注册和登录公开访问。骑手名称与手机号分别由数据库唯一键兜底；登录时禁用账号不能获得 Token。

------

## 已实现的 DeliveryTask 查询与动作

```text
GET /rider/delivery-tasks/available?radiusKm=5.0
    以骑手最后上报位置为圆心，半径内最多 100 个 GEO 候选按距离升序优先；
    其他 MySQL 可接任务按 ID 升序。位置或任务 GEO 失败、候选为空或无效时，
    按任务 ID 从新到旧返回最多 500 条；未上传位置会被拒绝

GET /rider/delivery-tasks/current
    查看当前骑手正在配送的任务

GET /rider/delivery-tasks/{taskId}
    查看当前骑手已接取任务的快照详情

PATCH /rider/delivery-tasks/{taskId}/claim
    接取配送任务

PATCH /rider/delivery-tasks/{taskId}/complete
    确认已经送达
```

以上接口都要求 JWT 角色为 `rider`，并要求 Rider 账号仍为正常状态。资源归属和状态约束由 `DeliveryTaskService` 再次校验。可接任务接口不分页，`radiusKm` 缺省 5 公里，且必须为有限正数。骑手位置缺失时要求先上传；附近查询故障或没有有效候选时仍从 MySQL 返回最多 500 条普通任务。

------

## 当前尚未实现

```text
查看骑手个人信息
骑手专用订单视图
骑手主动取消或转派任务
```

因此，当前 Controller 已闭环骑手账号、任务发现、抢单、当前任务、详情和确认送达；个人资料管理、历史任务分页、取消/转派仍属于后续范围。

# 十三、当前数据模型

## Rider

```text
id
name
phone
password
status
createTime
updateTime
isDelete
```

负责表达骑手身份和账号状态。

------

## DeliveryTask

```text
id
orderId
riderId
merchantName
deliveryReward
status
createTime
acceptedTime
deliveredTime
updateTime
receiverPhone
receiverAddress
merchantAddress
merchantPhone
receiverName
```

其中：

- `orderId` 非空且已有唯一索引，保证一张订单当前只对应一个配送任务；
- `riderId` 在任务创建时为空，接单成功后写入；
- 当前实体没有保存 `merchantId`，而是保存配送所需的商家、收货人与奖励快照；
- `acceptedTime` 和 `deliveredTime` 分别由抢单和确认送达动作写入。

------

## Order 需要的变化

新增状态：

```text
PAYING
PREPARING
READY
DELIVERING
DELIVERED
```

当前实际保存的业务时间：

```text
payTime
finishTime
```

当前 Order 没有 `acceptTime` 和 `readyTime`。骑手 ID、骑手接单时间和送达时间由 DeliveryTask 保存。

------

# 十四、当前明确不支持的边界

本次 MVP 暂不处理：

- 骑手接单与取餐的独立状态；
- 骑手主动取消任务；
- 骑手接单后转派；
- 无骑手接单后的超时处理；
- 自动派单和配送区域算法；
- 多骑手接力配送；
- 配送失败与重新派单；
- 生产环境支付与真实退款（当前仅启用 Stripe 测试环境，退款被明确阻止）；
- 商家、骑手收入结算；
- 用户评价系统；
- 消息推送；
- 已支付订单私下更换商品；
- 退款幂等、完整账单对账（Stripe 支付回调已接入）。

其中，`READY` 状态可能长期无人接单是已知边界。当前版本只保证流程能够闭环，不保证真实环境下的配送调度效率。

------

# 十五、最终最小闭环

```text
用户创建订单
    ↓
WAIT_PAY

用户支付
    ↓
PAYING
    ↓ 模拟支付成功
PAID
    ├─ 商家拒单 → CANCELLED（仅本地模拟订单，cancel_source=2，按版本尝试回补库存）
    │
    └─ 商家接单
          ↓
       PREPARING

商家制作完成
    ↓
Order = READY
创建 DeliveryTask = WAIT_ASSIGN

骑手接取任务
    ↓
DeliveryTask = DELIVERING
Order = DELIVERING

骑手确认送达
    ↓
DeliveryTask = COMPLETED
Order = DELIVERED

用户确认收货
    ↓
Order = FINISHED
```

这些状态和动作描述当前最小履约闭环，不代表所有风险已消除。尚未修复的请求标识比较、图片像素上限，以及 Docker 未实跑等验收边界见当前风险复核。
