## 3. 修复验收与剩余触发链

六个 HTTP 入口均 @Valid；公开路径鉴权先返回，参数校验在 Controller 方法、Service 账号查询和 Redis 限流之前。

V13已存在，不能改写其内容/校验和。保留全部历史SQL，[V20261014](../src/main/resources/db/migration/V20261014__restore_login_name_as_cs.sql)及同内容部署镜像先对三张表全部执行as_cs合并重名预检，再仅恢复三个登录字段的utf8mb4_0900_as_cs。冲突时明确中止，全部登录列尚未变更；不合并/删除账号，不改密码、ID、列长度或其他比较规则。deploy/schema三列同步为as_cs；业务库通过正常Flyway升级后生效。

验证范围：六入口非法字符返回参数错误400，三个业务Service均未调用；合法1/50字符及字母数字_-原样传入对应Service。真实三角色HTTP注册、登录及五次失败锁定；SQL仍能用零宽/Kelvin拼写匹配原账号，但非法HTTP输入先被BeanValidation拒绝，变体Redis计数保持0，原名保持5。迁移测试保留V12/V13历史证明，新增V14保值、其他列比较规则不变、重复执行、三角色两种重名预检和64字符/4096双字符as_cs权重检查。

### 3.2 准备重放：空车已修，剩较窄窗口

[OrderService](../src/main/java/org/example/takeout/Order/Service/OrderService.java)现捕获CART_EMPTY后再查原(userId,requestId)，存在则核对指纹并重放，不存在保持原错误。空车及不可用商品均使用该码。原“首查空→同key提交消费→读空车直接失败”链已修；匹配/不匹配指纹、没有原单、无事务副作用均有测试。

剩余现实交错：

**必须区分对照场景：** 如果原购物车一开始就超额，两个请求都未落单，原key确实不存在；补查仍为空、保持金额错误是正确行为。本项不是这个普通场景，而是下述“原单已成功提交后，又正常加购新商品”的额外交错。

1. 商品Q正常创建/上架，价格1000000.01（CreateDTO仍允许），有库存，店营业。
2. 同用户对原购物车发T1/T2，同requestId同参数；T2初查miss后暂停。
3. T1提交原单并消费购物车；用户正常加购Q。
4. T2恢复，读到新购物车，真实计价超过1000000，抛BUSINESS_ERROR。
5. catch仅回读CART_EMPTY，直接返回金额错误，未重放已提交原单。

真实MySQL/MockMvc测试固定上述交错：B首次查空且无外层事务；A通过HTTP提交并消费原购物车；用户通过HTTP加购正常创建/上架的Q；B恢复后执行实际结算并返回金额错误，随后在B同一线程通过真实OrderMapper按原key读到A的订单。断言只有一张订单、原商品只扣一次、新商品库存和新购物车均保留，后续同key重试返回A且不消费新车。对照测试也验证原车一开始超额、无任何提交时，两次合法请求均失败且原key确实不存在。

因此用户对“从未落单”的判断成立；剩余问题严格限定在“同key原单已经提交，又发生新加购”的交错。发生条件更多、仅响应错误，后续重试可重放，无重复订单/扣库，B/P2、较低发生概率。若业务接受此响应边界，可记录后冻结；订单业务代码本轮不改。

建议预期准备业务拒绝时按原key读回；已有原单且指纹相同则重放，否则保持原错误。数据库/程序异常不要无差别吞掉，不需长事务/长Header锁。CART_EMPTY与FILE_UPLOAD_ERROR数字码同2001，目前准备链无上传调用，不造成当前错分支，仅E表达问题。

### 3.5 最终审计修复：MVC 模板鉴权与三个局部 RC 事务

**编码路径角色绕过已修复。** 原来 `JwtInterceptor` 按 `AuthPathMatcher.normalizePath` 返回的原 URI 做角色分类；有效 USER/RIDER Token 请求 `/cat%65gory/products/image` 时，MVC 仍能映射到商家上传接口，而原 URI 未命中 `/category/**`。上传服务不读取商家上下文，因此错误角色能执行受格式及 5 MB 限制的图片写入。其他订单、商品和配送接口仍有资源归属/身份保护，不能扩大为任意他人业务数据读写。

当前 [JwtInterceptor](../src/main/java/org/example/takeout/Common/Interceptor/JwtInterceptor.java) 读取 `HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE`，缺少模板则拒绝，以已匹配的 `/category/products/image` 等模板调用 `assertRoleAllowed`。公开白名单仍使用原 URI；`ProductService.uploadImage` 没有新增服务层商家身份校验。修复在于角色分类与 MVC 实际路由一致，不是上传 MIME/路径规则变化。

**履约重复请求旧快照问题已修复。** 原默认 RR 事务在先读商家/骑手后建立旧快照；另一事务完成出餐、抢单或送达，重复请求的条件更新失败后，普通回读仍可能看到旧订单/任务并错误拒绝。本地事务与条件更新当时已防止半提交，但不能证明重复请求校验总能看到已提交目标状态。

当前 [FulfillmentService.completePreparation](../src/main/java/org/example/takeout/Merchant/Service/FulfillmentService.java)、[DeliveryTaskService.claimTask/completeDelivery](../src/main/java/org/example/takeout/DeliveryTask/Service/DeliveryTaskService.java) 三个事务入口局部使用 `Isolation.READ_COMMITTED`，继续保留 `rollbackFor = Exception.class`、归属、旧状态及未领取条件更新。后续回读获得已提交状态，全库隔离级别及其他业务入口不变；`OrderCommandService.acceptOrderByMerchant/markReadyByMerchant` 仍负责订单条件命令，不应把 RC 注解误归到这些方法。

`ProductService.updateProduct` 将缓存失效请求移到调用 `applyProductUpdate` 后的外层方法，外层 `@Transactional` 仍保留；PENDING 插入的 MANDATORY 和 afterCommit 语义未改变。

测试证明边界：订单重放的 MySQL API 测试沿用 mock 订单限流器，不作为真实 Redis 限流证据；Service mock 的 API 测试不证明真实文件写入。

### 3.6 商家 SSE、NEW 标记与前端接入边界

当前后端已提供商家专用的 `GET /merchant/events`、`GET /merchant/orders/unseen` 和 `PATCH /merchant/orders/seen`，都要求请求头中的商家 Bearer Token。支付事务的 `afterCommit` 尝试发送 `NEW_ORDER: refresh`；连接建立发送 `CONNECTED: connected`，每 30 秒发送 `heartbeat` 注释。SSE 只唤醒刷新，不携带完整订单，也不会自动确认已查看。

订单列表返回 `merchantSeen`。未查看查询只匹配当前商家、`PAID`、`merchant_seen = false`，按创建时间及 ID 升序；ACK 只更新同一条件下请求指定的订单，重复 ACK 不产生额外影响。`V20261017` 同步增加字段及五列复合索引，历史缺失值按状态 `0/1/2` 回填 `false`，其他状态回填 `true`，已有 `true` 与 `update_time` 保留。该次记录的迁移文件数已由后续版本更新，当前数量以本节 2026-10-26 再复核为准。

本轮已增加 `JwtInterceptor.afterConcurrentHandlingStarted`，在 SSE 转入异步时清除原请求线程的商家 ThreadLocal，避免等待连接结束期间残留身份；普通请求完成仍由 `afterCompletion` 清理三类上下文。

本仓库不含前端。首次打开/重连补查、刷新订单、显示 NEW、实际进入可见界面后 ACK 是尚需前端接入的契约，不能写成端到端已实现。连接表只在当前进程内保留每商家一条连接，多标签页会替换旧连接，支付请求不会自动广播到其他实例。SSE 事件没有持久化、事件 ID 或重放；连接恢复后的数据库补查能恢复仍未查看的待接单订单，但不能保证每条事件实时送达或人在页面上真正阅读。详细决策见 [NEW 标记 ACK 文档](merchant-order-new-marker-ack-decision.md)。

本轮新增回归范围：`MerchantSseServiceTest` 覆盖建连、替换连接、心跳及异常清理；`MerchantSseMvcTest` 通过 MVC 验证商家鉴权、其他角色拒绝和 SSE 转异步后的商家上下文清理。`MerchantOrderSeenDatabaseTest` 使用真实 H2 Mapper 与 MVC 覆盖未查看查询、列表标记、展示后 ACK 再查询、重复 ACK 及跨商家隔离；`OrderPaymentNotificationTransactionTest` 使用真实 H2 SQL 和 Spring 事务覆盖支付成功提交后通知、提交前不通知及回滚不通知。旧 MySQL 夹具中的 `CartServiceIntegrationTest`、`OrderServiceIntegrationTest`、`OptimisticLockIntegrationTest` 同步补齐 `merchant_seen` 列，避免禁用 Flyway 时沿用旧表结构。

上述 H2 与隔离测试无需 MySQL/Redis，证明的是本轮后端行为；它们不替代 `V20261017` 的真实 MySQL 迁移、索引、历史回填测试，也不证明前端页面已接入或跨实例广播已经实现。

本轮新增 27 项回归：SSE 服务 9 项、SSE MVC 7 项、ACK 数据库闭环 4 项、支付事务通知 6 项，以及旧 MySQL 测试库初始化 1 项。最后一项位于 `FlywayMigrationIntegrationTest.legacyMysqlTestFixtureBackfillsSeenAndPreservesAcknowledgementsOnRepeat`，在随机临时库中验证补列回填保留时间戳、重复初始化保留已确认标记、新订单默认未查看。

## 4. 重新证明不变量与异常数据边界

### 4.1 User → Header → 鉴权 → Cart

当前生产 User 插入路径是 [register](../src/main/java/org/example/takeout/User/Service/UserService.java)，用户插入及 Header 初始化在同一事务。[CartHeaderManager.insertCartHeader](../src/main/java/org/example/takeout/CartHeader/Manager/CartHeaderManager.java) 要求 MANDATORY 且校验影响行数；失败使注册回滚，不会先提交 User 再留下缺 Header。现有生产代码没有删除 User/Header 的 HTTP 功能；登录和受保护请求还复核当前 User 存在及状态。

[V20261010](../src/main/resources/db/migration/V20261010__cart_header_backfill.sql) 为历史用户补 Header 并按购物车修正绑定；迁移拒绝多商家、孤儿用户和非法商家 ID。它**没有**验证 CartItem/Product 商家一致等所有历史不变量，不能把预检范围扩大。应用 [FlywayConfig](../src/main/java/org/example/takeout/Config/FlywayConfig.java) 启动执行迁移，失败阻止正常启动；被人为禁用迁移或旧库未升级是环境异常前提。

[CartService.list](../src/main/java/org/example/takeout/Cart/Service/CartService.java) 对缺 Header 解引用确实可能 NPE，Checkout 缺 Header 会返回空结果。但在上述正常调用链下无法形成缺行状态。结论是 **C：异常数据/防御性健壮性问题，正常业务路径不可达**，不是普通购物车 bug，不要求冻结前增加自动修复数据逻辑。

### 4.2 Header / CartItem / Product 的商家一致性

[CartService.add](../src/main/java/org/example/takeout/Cart/Service/CartService.java) 在事务内锁定同一用户 Header，首次绑定取已查到的 Product.merchantId；CartItem.merchantId 也取同一商品对象。已有绑定与新商品商家不同则拒绝。update/delete/clear/checkout 消费都使用同一 Header 锁；最后一条明细删除后解绑。Product.merchantId 只在创建时按当前商家设置，UpdateProductDTO 没有该字段，未找到正常改归属路径。

因此正常生产写入不能持久化这三方商家 ID 不一致。读方没有再次逐行 assert，并不改变此结论。

需要区分**多次读取的临时混合快照**：准备阶段可能先读店 A 明细，然后另一个合法请求清空并加购店 B，准备再读到 B Header。这个状态并非只能脏数据触发。但是换店必须删除 A 明细；落单时 [CartCommandService](../src/main/java/org/example/takeout/Cart/Service/CartCommandService.java) 按旧明细 ID/足够数量条件消费，旧行不存在即报错并整体回滚，不能据此提交错商家订单。list 可能出现暂时的展示混合，不是三方持久化一致性 bug。现有锁与条件消费也不是零并发失败保证。

### 4.3 商家营业状态和公共 Service 的真实能力

merchant.status 是 `TINYINT NOT NULL`，因此迁移后的正常表不能存 NULL；没有永久 `IN(0,1)` CHECK，因此未知整数不被数据库禁止。注册强制 CLOSED，MerchantUpdateDTO 不含 status，当前唯一生产状态写入由 [Controller](../src/main/java/org/example/takeout/Merchant/Controller/MerchantControllerSold.java) 的 `@Min(0) @Max(1)` 限制；API 测试拒绝非法值。

**不能声称公共 Service 自身已完整防护**：[MerchantAccountService.updateStatus](../src/main/java/org/example/takeout/Merchant/Service/MerchantAccountService.java) 只对 null 返回，直接 Java 调用 `updateStatus(2)`、且上下文有效，确实能持久化未知值。当前检索到的唯一生产调用者是受约束的 Controller，所以没有正常 HTTP 触发链。非法状态下 list 必须 OPEN、Checkout 只排除 CLOSED 的分歧应归 C/P3。

同理，ProductService 的公共 DTO 方法不自动执行完整 Bean Validation；绕过 Controller 传负库存/非法价格可能写入异常数据。CartHeaderManager 的低级绑定方法也不是“任意调用仍保持全部关系”的领域防火墙。本文保证的是**现有合法生产调用协议**，不是所有 public 方法接受任意伪造参数都安全。库存命令自身另有正数量校验，Cart/缓存命令通过 MANDATORY 限制事务。

### 4.4 默认分类、外键与配送状态

商家注册事务初始化固定默认分类；普通分类创建显式设置普通类型，默认分类不可删除，没有分类改名/改类型的正常入口。缺默认分类、多默认分类、跨商家分类或孤儿关系，当前未找到合法 HTTP 写入链。数据库仅部分关系有外键，默认类型/许多数值状态没有 CHECK，这是 C 的兜底缺口，不能凭“缺外键”直接列 P0。旧空名、金额溢出及单次极值库存重置链已由本次修改阻断，不与这些异常前提混为一谈。

[商家出餐](../src/main/java/org/example/takeout/Merchant/Service/FulfillmentService.java) 将 READY 和建配送任务放在同一事务，任务 order_id 唯一；[抢单/送达](../src/main/java/org/example/takeout/DeliveryTask/Service/DeliveryTaskService.java) 通过归属/状态条件和同一事务推进任务及订单。用户确认后骑手重复完成允许 DELIVERED/FINISHED。直接调用内部状态命令而不执行建任务编排可以制造异常组合，但这属于绕过现有履约入口，不能推翻正常事务闭环。

## 7. 冻结决策所需结论

1. **当前P0/P1：** 编码角色绕过和旧快照重试问题已修复；request_id 比较、图片像素上限仍为未修 P1。没有把无正常制造路径的缺 Header、持久化错商家提升为 P0。
2. **冻结前值得修的P2：** 仅同key已提交后遇到非CART_EMPTY准备业务拒绝的响应重放窗口。用户若接受此较窄响应边界，可记录后冻结；五项A已修，不重复留待办。
3. **可以接受并记录：** 准备报价/商家快照、缓存最终一致、Redis限流fail-open、购物车增量非幂等、加入时展示价/准备价结算、更新零价/多小数/名称必填、库存按执行顺序。历史永久保图、重置必须为最终值、外部客户端兼容仍是需求边界。
4. **仅defensive programming：** 缺Header、手工破坏商家关系、未知状态、缺默认分类、孤儿、伪造内部参数。可增强提示/兜底，不因读方少assert自动归A/B。
5. **规模扩大后：** Outbox聚合/claim/到期索引/清理，超时批次/退避/监控，多实例上传存储，已删图片占用、极端INT数量容量。吞吐量级100/(处理耗时+60s)，没有固定100单/分钟保证。
6. **停止重构/冻结V2：** 停止架构扩展和大规模重构；再决定是否花有限时间处理两项剩余 P1。P1 按本轮标准不是封存硬阻塞，但必须明确接受/记录；Docker 未实跑则保留验收缺口。不要凭历史测试宣布零风险、封存全部完成，也不因 C/D/E 的治理边界继续投入。

## 8. 2026-10-26 工作区静态复核

本节更新其后发生的实现和文档变化；第 3 节 2026-10-19 的测试结果只表示当日实际运行范围，本次没有重跑它们。

- **现存 P1 未见代码层修复：** `orders.request_id` 仍按 `utf8mb4_0900_ai_ci` 比较；商品图片入口仍直接调用 `ImageIO.read`，没有先限制像素数。它们仍是第 2 节的遗留项目。此前确认的路由模板角色检查、履约 RC 重试和 NEW 标记不因为本次复核而回退。
- **订单取消原因已入库：** `V20261018__order_cancel_source.sql` 增加可空 `orders.cancel_source`；当前用户取消、商家拒单、超时取消分别写入 `1/2/3`。历史取消保持 `NULL`，平台取消 `4` 尚无入口。商家重复拒单只在所属商家一致且取消来源为商家时返回成功。
- **库存补偿现在区分库存基准：** 最新迁移 `V20261026__stock_version.sql` 增加 `product.stock_version` 和 `order_item.stock_version`。下单事务锁定商品行后读取版本，按版本扣减并将该次版本写入明细；商家显式提交库存值（包括数值不变）会推进基准。取消时只对版本仍匹配的明细回补，版本不匹配的旧订单数量跳过，避免把旧基准的库存加到商家新设值上。相关边界及实体字段见[数据库结构](数据库结构.md)、[状态流转](状态流转表.md)。
- **缓存任务清理不再是“成功记录缺少清理”：** PENDING worker 第 5 次失败转为 FAILED，短周期退避为 10/30/60/120 秒；FAILED 按小时重试。SUCCESS 记录按创建满 7 天清理，每轮最多 1000 条；PENDING 和 FAILED 不自动清理。因此剩余规模治理是任务聚合/领取、到期索引和非终态积压，不应把 SUCCESS 清理写成尚未实现。
- **新建商品会登记详情缓存失效：** `ProductService.createProduct` 在新 ID 创建后请求同事务 PENDING 任务，提交后立即删除；失败仍由任务重试。新建商品遮挡先前 `__NULL__` 空值缓存的问题已处理，边界仍服从已接受的缓存最终一致性。
- **Redis GEO 骑手位置服务有实现，但没有主代码 Controller 调用：** `rider:locations` 保存坐标、`rider:last_active` 保存最近上报时间；满 5 分钟无更新后清理，清理调度为执行完成后等待 5 分钟，每轮至多 1000 个成员；附近查询按距离取前 100 个，不校验 last-active 新鲜度，直到清理轮次移除过期成员。不能据此称为已接入的骑手位置 HTTP API 或配送派单流程。服务与调度器有单元/Redis 集成测试源码，但本次未运行测试。
- **迁移文件数量已更新：** `src/main/resources/db/migration` 与 `deploy/migrations` 各有 18 份 SQL（1 份空库基线、17 份版本迁移），最新为 `V20261026__stock_version.sql`。这只核对仓库文件，不证明任何部署数据库已应用该版本；仍需按库检查 `flyway_schema_history` 与实际列定义。
