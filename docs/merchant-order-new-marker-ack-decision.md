# 商家新订单提醒与 NEW 标记 ACK 决策

状态：已采纳  
记录日期：2026-10-17  
涉及范围：商家订单列表、SSE 新订单提醒、断线重连补偿  
实现核对：2026-10-19；本仓库仅有后端，下文页面展示、重连补查和 ACK 时机均为前端接入契约，尚无前端实现可验收。

## 先说结论

当前设计保留前端 ACK，不改成“后端发送 SSE 后立即把订单标记为已查看”。

这里的 ACK 主要服务于页面上 **NEW 标记的生命周期**，并不是单纯为了证明 SSE 有没有成功发送。后端本来就知道哪些订单需要提醒，订单 ID 从后端传给前端、再由前端带回来，也不是为了让前端重复告诉后端这些 ID 是什么；这次返回代表的是另一件事：前端已经把这批订单作为“新订单”处理并展示，可以结束它们的 NEW 状态了。

换句话说，`merchantSeen` 更接近“这笔待接单订单是否已经进入过商家的可见界面”，而不是“后端是否调用过一次 `SseEmitter.send()`”。

## 为什么不能在 SSE 发送后马上更新

`SseEmitter.send()` 没有抛出异常，只能说明后端当时没有发现连接已经坏掉。它不能证明浏览器已经收到事件，更不能证明页面已经完成刷新和展示。

更直接的问题是，当前 SSE 的 `NEW_ORDER` 事件只负责告诉前端“订单有变化，请刷新”，完整订单仍然通过 `/merchant/orders` 获取。如果后端发送完 SSE 就立即把 `merchant_seen` 更新为 `true`，很可能出现下面的时序：

```text
新订单支付完成，merchant_seen = false
        ↓
后端发送 NEW_ORDER: refresh
        ↓
后端立刻更新 merchant_seen = true
        ↓
前端刷新 /merchant/orders
        ↓
拿到的订单已经不是 NEW，页面第一次展示时反而没有“新”标记
```

连接也可能恰好在“后端写出事件”和“浏览器收到事件”之间断开。如果这时已经由后端标记为已查看，商家重连后就无法再得到这次提醒。相比偶尔重复提醒一次，悄悄漏掉一笔待接单订单的代价更大，所以当前方案选择保留 ACK。

## 当前链路

一笔订单的 NEW 生命周期如下：

1. 用户支付成功，订单进入 `PAID`，`merchant_seen` 保持为 `false`。
2. 支付事务提交后，后端通过 SSE 发送 `NEW_ORDER`，提醒在线商家刷新订单。
3. 商家首次打开页面或 SSE 重连时，前端应调用 `/merchant/orders/unseen`，取得当前仍未确认查看的 `PAID` 待接单订单 ID，结果按创建时间、ID 升序。
4. 前端通过 `/merchant/orders` 获取完整的 `MerchantOrderListVO`，展示订单内容和 NEW 标记。
5. 这批订单已经进入可见界面后，前端批量调用 `PATCH /merchant/orders/seen`。
6. 后端只把“属于当前商家、仍处于 `PAID`、当前尚未查看”的指定订单更新为 `merchant_seen = true`。
7. 之后即使连接再次断开，这些尚未接取但已经展示过的订单仍会出现在待接单列表里，只是不再作为 NEW 重复提醒。

这几个入口看起来都和订单列表有关，但回答的问题不同：

| 入口 | 回答的问题 |
| --- | --- |
| `GET /merchant/events` | 现在是否发生了值得刷新页面的变化？ |
| `GET /merchant/orders` | 当前订单的完整展示数据是什么？ |
| `GET /merchant/orders/unseen` | 哪些待接单订单还没有进入过本次商家的可见提示？ |
| `PATCH /merchant/orders/seen` | 哪些 NEW 标记现在可以结束？ |

这四个接口都只允许商家身份，必须携带 `Authorization: Bearer <token>` 请求头，SSE 不接受 URL 中的 Token。前端需选择支持自定义请求头的 SSE 客户端，并设置 `Accept: text/event-stream, application/json`，同时接受正常事件流和鉴权失败 JSON。鉴权失败响应沿用 HTTP 200、业务 `code=401` 的约定，客户端需检查响应类型和业务码；当前没有对仅接受 `text/event-stream` 的严格 SSE 客户端提供错误协商兼容保证。连接建立时后端发送 `CONNECTED` 事件、数据为 `connected`；新订单发送 `NEW_ORDER` 事件、数据为 `refresh`；定时任务每 30 秒发送 `heartbeat` 注释。ACK 请求体直接使用订单 ID 数组，例如 `[101,102]`；空数组不更新任何订单。

`merchantSeen` 默认 `false`，订单列表查询和 SSE 发送都不会改变它。ACK 确认只限定提交的订单 ID，不会清除同商家同时新到的其他订单标记。

## 这里所说的“看见”到什么程度

ACK 也不等于证明商家的眼睛真的读过订单。后端和前端都无法可靠判断人的注意力，它表达的是一个更务实的边界：页面已经收到并展示了这批订单，前端愿意结束它们的 NEW 标记。

订单一旦被商家接取，就离开了 `PAID` 待接单状态，NEW 提醒的业务生命周期也随之结束。`merchantSeen` 只用于判断待接单订单是否需要作为新订单提示，不应被解释成订单全生命周期的阅读记录。

## 断线和重复请求如何处理

- 商家离线时产生新订单：数据库里的 `merchant_seen = false` 会保留下来，重连后由 `/orders/unseen` 找回。
- SSE 事件丢失：不会影响订单本身，页面重新打开或连接恢复后仍能补查。
- 页面已经展示，但 ACK 请求失败：订单下次可能再次显示为 NEW。这是可以接受的重复提醒，比漏掉订单更安全。
- ACK 被重复提交：更新条件只匹配当前仍未查看的订单，因此重复请求不会产生额外业务影响。
- 请求夹带其他商家的订单 ID：更新仍受当前登录商家 ID 限制，不能跨店修改。

这套方案允许失败边界上的重复提醒，并保留尚未确认展示的订单供后续补查。它不提供消息“至少一次投递”的保证；补偿依赖前端实际执行补查及展示后 ACK，不能仅凭 `SseEmitter.send()` 返回成功判定已经提醒到商家。

## 当前连接与部署边界

每个应用进程使用内存表，按商家 ID 只保留一条 SSE 连接。新连接会完成旧连接，多标签页或多设备连接同一进程时会互相替换。旧连接的完成/异常回调只移除该连接，不应误删替代它的新连接。发送事件或心跳失败时，后端清理连接，交由客户端重连。

支付事务只通知当前进程内的连接。多实例下，商家连接与支付请求若落在不同实例，不会自动收到实时提醒；当前没有跨实例广播、持久化事件、事件 ID 或回放游标。重启会清空连接，恢复后仍依赖首次打开或重连时的数据库补查；持续连接中的事件丢失也不会自动触发重连补查。如需覆盖这种窗口，前端可增加主动刷新/定期补查，或另行实现可靠通知方案。

SSE 转入异步后，`JwtInterceptor.afterConcurrentHandlingStarted` 清理原请求线程的商家身份；这项清理防止请求线程残留 ThreadLocal，不代表连接存续期间会持续复核 Token 或商家资格。

## 数据库落地

`V20261017__merchant_order_seen.sql` 与 `deploy/schema.sql` 都包含 `merchant_seen TINYINT(1) NOT NULL DEFAULT 0` 和 `(merchant_id, status, merchant_seen, create_time, id)` 五列复合索引。迁移将缺失标记的历史 `WAIT_PAY/PAYING/PAID`（状态 `0/1/2`）回填为 `false`，其他状态回填为 `true`；已有 `true` 保留，其他状态已有的 `false` 也归为 `true`，回填不推进 `update_time`。未支付历史订单后续支付时仍能作为 NEW 出现，已离开待接单阶段的历史订单不会在上线后集中提示。

## 接受的成本

保留 ACK 意味着前端需要多发一次批量请求，也需要在成功展示订单后选择合适的时机提交确认。这不是为了补齐后端缺少的订单信息，而是为了让 NEW 状态有一个可信、清晰的结束点。

当前认为这点复杂度是值得的：SSE 继续只承担轻量的实时唤醒，REST 接口继续提供完整订单数据，数据库中的 `merchantSeen` 则负责跨刷新、跨断线保存 NEW 标记状态。三个职责没有混在一起。

## 什么时候需要重新讨论

下面这些需求出现时，应重新评估当前方案：

- 产品决定“后端尝试发送过就算已提醒”，不再关心页面是否展示；此时可以去掉 ACK，但字段含义也应改成 `merchantNotified` 或 `notifiedAt`，避免继续叫 `Seen`。
- 需要区分同一商家的多个设备或多个操作员分别是否看过；单个订单字段不够，需要独立的查看记录。
- 需要严格回放每一条 SSE 事件；届时应增加事件 ID、持久化事件或 Outbox，而不是让 `merchantSeen` 同时承担消息队列游标的职责。
- NEW 标记不再按订单维护，而只需要一个新订单数量；届时可以改成商家维度的游标或最后查看时间。

在这些需求出现之前，维持当前设计：**SSE 负责叫醒页面，订单接口负责提供事实，前端 ACK 负责结束 NEW 标记。**
